# STEP 5 設計案（詳細化・実装開始前の確認用）

2026-10-21更新。設計確認後のユーザー承認に基づきSTEP 5を実装。実行方法・実装上の制限はSTEP5_USAGE.mdを参照。既存のゲームルール、点数、Collider、物理設定、手動操作を変更しない。

## 1. 初版の構成と変更できる設定

既存のSuikaPhysicsSimulatorを使い、同じ開始盤面から複数の1手先を予測する。最初は1種類の高得点AIとする。

| 設定案 | 初期値・許容範囲 | 用途 |
|---|---|---|
| candidate_count | 5、整数2〜31 | 等間隔候補。9・11・21・31へ設定変更できる |
| post_drop_steps | 25、整数1〜150 | 既存の比較用通信が扱える範囲を再利用。25・50・100を比較可能 |
| height_bins | 9、整数2以上 | 凹凸を測る横分割数。候補数とは独立 |
| score_scale | 55、正数 | 得点を評価値の尺度へ変換。実ゲームの点数は変更しない |
| weight_roughness | 0.2、非負 | 偏りの減点係数。H/Dは分析用のみ。旧weight_dangerは無効 |
| danger_band_fraction | 0.15、0より大きく1以下 | 籠内高の上側15%を初期の危険帯とする |
| uncontacted_risk_weight | 0.5、0〜1 | まだ接触していない落下果物の危険度係数 |
| planning_budget_ms | 0＝初版は全候補計算 | 任意に設定するソフトな計算時間上限 |

これらは将来のPlanningSettingsとしてInspectorから設定可能にする案。1回の探索開始時に設定一式を固定し、途中の変更は次回から適用する。使用設定・評価方式versionを結果に記録する。上限は初版の入力検査の範囲であり、Unityの物理設定ではない。

候補は浮動小数点除算で x_i = i / (candidate_count - 1), i=0,...,N-1。5候補なら [0, .25, .5, .75, 1]。世界Xは既存GetDropRange/GetDropRangeForFruitのmin_x/max_xを使って補間する。壁の内面、現在保持する果物の有効ColliderのOffset・Scale・形状、接触余白、Collider.Distance検査をそのまま利用する。固定Xや全果物共通の半径を新設しない。範囲が無効、または幅が0で複数位置を作れない場合は探索エラーとして操作せず、壁や形状を変更して回避しない。

## 2. 同一盤面と実際の操作の整合性

初版はUnityのメインスレッドで、1回の命令受付内に「設定固定→開始状態固定→N候補を独立予測→評価→選択→既存step予約」まで同期的に完了する。候補計算の途中では実ゲームの物理更新を呼ばず、Time.timeScaleも変更しない。候補を1つ予測した後の結果を次の候補の初期状態にしない。

既存Predictは同期実行なので、同じ受付内で順に呼び出す間、ライブ盤面は物理的に進まない。初版は新しい完全復元システムを作らず、この性質を利用する。元盤面・スコア・乱数状態の不変を検査し、各候補で同じ保持果物・見えているNEXT・移動速度・残り落下待機時間を使う。未公開の未来の果物や乱数状態をAIへ渡さない。

操作対象の果物ID、episode_id、初期状態の識別情報、設定一式をdecisionに残す。選択後は同じ受付内で操作を予約し、次の通常FixedUpdateから既存stepを動かす。描画の引っ掛かりやその後の複数FixedUpdateの可能性は測定対象であり、物理時間を消したり停止させたりして隠さない。

将来Pythonモデルへ判断を往復させる場合は、episode_idとphysics_revisionを含むsnapshot tokenを導入し、操作直前に一致を検査する案。不一致なら操作せず再取得/再評価する。state_idだけでは観測間の物理進行を識別できない。このtoken機能や学習用の時間制御は今回まだ実装しない。

## 3. 評価対象の果物と基準座標

評価は予測終了時点で行う。次の集合を明示的に分ける。

- B（全盤面果物）：現在の数値観測と同じ役割判定による、active、非preview、非mergingの盤面果物。今回落とした果物・合体生成果物を含む。削除待ちの合体元は含めない。名前の文字列で検出しない。
- C（接触盤面）：Bのうち、その時点で床・壁・別のBの果物と有効な非Trigger接触がある果物。予測シーン内のContact情報で取得する。HasCollidedだけで「現在接触中」と判断しない。接触中でも完全静止・床に支持されている保証はない。
- A（空中等）：BからCを除いた果物。未接触の落下果物だけでなく、一度触れた後に跳ねて接触を失った果物も含む。
- 保持中・NEXT：B/C/Aのすべてから除外。今回の落下後にNEXTから生成される次の保持果物も除外する。ただし判断材料からは除外せず、decisionに開始時のheld_fruit_type/next_fruit_typeを保持し、将来の評価関数から参照できる。未表示のさらに先の果物は取得しない。

HとRはCを使い、まだ高い場所を落下中の果物を固定した積み上がりと混同しない。DはBすべてを使い、空中だから安全とは扱わない。空中果物の個数・最大Collider上端も診断値として記録する。短い予測ではCにまだ入らず将来の積み上がりを十分に評価できない場合があり、予測時間比較で検証する。

高さの基準は、Inspectorで明示参照する既存の籠の床Collider上面 y_floor と、実GameManager.GameOverHeightの y_go。L = y_go - y_floor。左右内面は既存の安全範囲計算から取得する。床を名前だけで自動決定しない。床参照の欠落・非対応形状、L<=0、左右内幅<=0は設定エラー。現在の水平な床・直立壁を対象とし、形状やTransformは変更しない。

## 4. H・D・Rと評価式

clip01(z) = min(1, max(0,z)) とする。各予測シーンの実Collider.bounds（回転・Scale・Offset込み）と果物のTransform中心座標を使う。描画画像の大きさや固定の半径は使わない。

### H：接触盤面の最大高さ（0〜1）

Cの果物fについて h_f = clip01((Collider上端Y_f - y_floor) / L)。
H = max(h_f)、Cが空なら0。

Collider上端で測る「占有高さ」であり、実ゲームの中心座標によるGO判定とは別の評価特徴。clamp前の高さとライン超過量も診断に残す。現在は分析値として残すだけで、Hによる減点は行わない。

### D：ライン付近の危険度（0〜1）

b = danger_band_fraction * L。
Bすべての果物fについて、中心座標y_fから q_f = clip01((y_f - (y_go - b)) / b) を計算する。

- HasCollided=trueなら w_f=1。空中へ跳ねてもこの重みを保つ。実ゲームも一度接触すると接触済みを維持するため。
- HasCollided=falseなら w_f=uncontacted_risk_weight（初期0.5）。落下途中でまだ接触していない果物も、ライン上や近傍なら減点する。
- D = max(w_f * q_f)、Bが空なら0。

初期値では危険帯の下端で0、ライン以上で接触済みなら1・未接触なら0.5。係数2は最大2の減点。0.15と0.5は調整可能な仮の評価パラメーターであり、実測済みの誤差上限や安全保証ではない。実ゲームのGOラインや接触条件を緩めるものではない。予測GO=falseでもDは通常どおり計算する。

### R：高さのばらつき（0〜1）

籠の左右内面の間をheight_bins個の等幅区間に分ける。各区間jの高さh_jは、その区間とCollider.boundsのX範囲が重なるCの果物のh_fの最大値。果物がない区間は0。区間は左閉右開、最後だけ右端を含むものとし、接する端だけで隣区間を占有したと数えない。

h_mean = (sum h_j) / K。
R = clip01(2 * sqrt(sum((h_j - h_mean)^2) / K))。

母標準偏差を用いる。[0,1]の高さの標準偏差は最大0.5なので2倍して[0,1]へ正規化する。係数0.2は最大0.2の減点。高くても平らならRは小さいがHで減点される。boundsによる横方向の占有は評価用の近似であり、Circle/Capsuleの輪郭そのものに沿う精密な高さプロファイルではない。物理Colliderは変更しない。

### 得点と最終評価

S_startを候補予測開始時の得点、S_endを終了時の得点とし、delta_score = S_end - S_start。

V_base = delta_score / score_scale - weight_roughness * R

初期値を代入すると V_base = delta_score/55 - 0.2R。

55点の増分を評価値+1に換算するだけであり、得点項は[0,1]へclampしない。複数合体なら1を超えてよい。D/Rの重みを得点に換算すると、最大でそれぞれ110/11点相当の減点になる。Hの減点はない。これは初期の尺度合わせであり、高得点につながる係数だと検証済みではない。

## 5. 予測ゲームオーバーと候補選択

予測中に一度でも既存のGO条件が成立して停止した候補は predicted_game_over=true とする。評価器が独自のGO条件や猶予時間を新設することはない。

通常選択の数式は、候補cが計算成功・落下成功・predicted_game_over=falseなら V_select(c)=V_base(c)、それ以外は V_select(c)=-infinity。これにより、大きい加点で予測GOを打ち消すことはない。通信JSONにInfinityを入れず、除外候補はselection_score=nullとexcluded_reasonを記録する。計算に成功したGO候補は診断用のV_baseを計算するが、通常候補とは競わせない。

非GOの有効候補がある場合はV_base最大を選ぶ。評価値が絶対差1e-6以内なら同点として、予測内の落下までの時間が短い→候補indexが小さい、の順に決める。NaNや無効な形状は候補失敗であり、安全な0点として扱わない。

全要求候補を評価でき、すべてがGO予測の場合だけ、status=all_predicted_terminalとして次の辞書式順序でフォールバックする。

1. 予測開始からGO成立までのゲーム内時間が長い候補。
2. 同じなら、終端時の「接触済み果物の最大中心Y - y_go」の正の部分をLで割った超過量が小さい候補。この超過量はclampせず、Dが1に飽和した場合を区別する。
3. 同じならV_baseが大きい→候補indexが小さい。

この場合の採用も安全とは報告せず、予測GO・成立tick・フォールバック理由を明示する。移動中GOで落下前に終了した候補も有効な終端予測として含める。選択後の既存stepも、実GOが起きれば落下せず終端を返し得る。

失敗・未評価の候補が残る場合は「全候補GO」と呼ばない。非GOの有効候補があればpartial_planを明示してその中から選ぶ。非GO候補が1つも確認できず、失敗・未評価もある場合はno_nonterminal_evaluatedとして操作せず返す。全失敗も探索エラー。実ゲームが既にGOなら探索/落下せず、resetを要求する。

## 6. 予測時間と加点区間

post_drop_stepsは設定値を既存Predictへ渡す。移動中・落下制限の待機中も、通常と同じfixedDeltaTimeで盤面を進める。実効移動速度と残り待機時間を再利用し、描画アニメーションには依存しない。

既存stepの数え方を維持する。落下を実行した物理更新を0番目として、その後post_drop_steps回を数えて完了する。したがって25設定は、その後のゲーム時間が約0.5秒（fixedDeltaTime=0.02時）であり、落下した更新自体も含めると落下以降のSimulate呼出しは26回になる。移動時間から25回を数え始めたり、この違いを隠すために物理更新を追加/削除したりしない。

| post_drop_steps | 落下更新後の公称ゲーム時間（dt=.02） | 用途 |
|---|---:|---|
| 25 | 約0.5秒 | 初版 |
| 50 | 約1秒 | 落下途中や遅い合体の比較 |
| 100 | 約2秒 | 連鎖・危険度と計算時間の比較 |

同じdecisionの全候補に同じpost_drop_stepsを適用する。GOなら途中終了し、要求値と実際の更新数を分けて記録する。完全静止は待たない。dt、移動/待機/総物理更新数、drop_tick、GO tick、各段階のゲーム時間を記録し、壁時計の計算時間とは区別する。

加点は各物理更新の直前・直後の得点差で、次の排他的な3区間へ加算する。

- movement_reward：まだ落下しておらず、その更新で横移動した場合。
- cooldown_wait_reward：まだ落下しておらず、目標位置で落下制限の解除を待った場合。
- post_drop_reward：落下を実行した更新と、それ以降。到着と落下が同じ更新なら、その更新の物理演算による加点はすべてここへ含める。

pre_drop_reward = movement_reward + cooldown_wait_reward。
通常は delta_score = pre_drop_reward + post_drop_reward = S_end - S_start を検査する。後述の物理更新外加点がある場合も含めた一般形は delta_score = movement_reward + cooldown_wait_reward + post_drop_reward + other_in_step_reward。例外的な加点もこの保存則から除外しない。

S_dropは実際のDropFruitを呼ぶ直前のスコアとして保存する。落下前にGOならS_drop/drop_tickはnull、post_drop_reward=0とし、実行できていない落下を成功扱いしない。移動tick数の既存カウンターは落下と同時の移動を含むため、加点区間のtick数とは区別して名前を付ける。

実ゲーム側も既存stepの受付/完了のledgerを保ち、その内部に同じ物理更新区分の加点内訳を追加する方針。合体得点は通常の衝突コールバックが発生する物理更新に帰属させる。物理更新の外の加点が検出された場合はother_in_step_rewardへ別記録し、保存則へ含めて警告する。初版の通常ゲームではこの値が0になることを検査し、移動/落下後へ勝手に混ぜない。予測も同じ保存則を検査する。

思考前やstep終了後の加点は、既存reward_accountingのbetween_stepsとして別に保持し、候補のdelta_scoreに加算しない。UnityEnvのrewardは従来どおりstep中の加点合計とし、内訳はinfoで返す。時刻区分であって行動の因果関係を主張しない。

初期の選択は移動中の自然加点も含むdelta_scoreを使う。移動中の盤面進行も実際の候補結果の一部だからである。ただし、その加点を落下場所の成果とは呼ばない。ログから「得点項全体」と「落下後の得点項だけ」による順位、移動時間と事前加点の関係を分析する。初期は診断上の比較にとどめ、選択式を自動変更しない。異なる時間の加点を1秒あたりに割る補正や、加点原因の推測は入れない。

## 7. 各候補で必ず確認できる結果

既定で全要求候補のコンパクトな結果を返し、ローカルに保存できる設計とする。

- decision_id、episode_id、action_id、初期観測/盤面識別、保持果物ID、candidate index、要求X/世界目標X/実適用X。
- evaluation_version、使用設定一式または参照可能なconfig_id、要求候補数/評価済み数、post_drop_steps、fixedDeltaTime、実効速度、安全範囲、床上面/GO高さ。
- 計算成功/落下成功/予測GO、選択可否、除外・失敗理由、フォールバック/partial_planの有無、選択された候補。
- H/D/R、得点項、各重み付き減点、V_base、selection_score、Dを最大にした果物と接触済みフラグ、対象B/C/Aの個数。
- S_start/S_drop/S_end、movement/cooldown_wait/pre_drop/post_drop/other_in_stepの加点、合体イベントの種類とtick、保存則の成否。
- 移動/待機/落下後/総物理更新数、drop/GO tick、段階別ゲーム時間、Scene生成/コピー/Simulate/解放予約・探索全体の壁時計時間。

完全な予測果物状態や毎tickの軌跡は詳細診断のオプションにし、通常は大量保存しない。予測の果物IDは候補ごとのものなのでdecision/candidateと組にして扱う。実行後には予測と実結果を対応付ける。生ログは既存方針どおりGitへ含めない。

## 8. 実装の分担と将来の差し替え

実装開始後の最小案：既存SuikaPhysicsSimulatorに評価用の形状/接触特徴と加点区間を追加し、シーンを解放する前に取得する。既存JSONの種類/位置だけからColliderや現在接触を推測して復元しない。評価計算は小さいHeuristicEvaluator、候補生成・予測・選択はStepPlannerに分ける。大きなプラグイン基盤やモード切替は作らない。

概念上はCandidateOutcome→Evaluate(features, settings)→EvaluationBreakdown、候補一覧→Choose→Decisionの境界を保つ。初版はUnity内の関数でよい。将来Value Networkで評価を置換し、MCTSで選択/分岐方法を置換しても観測・操作・物理基盤を再利用できるようにする。現Predictはライブ盤面の1手用で、多手の任意分岐状態復元は別段階である。

Python側は将来UnityEnv.plan_step()のような入口で既存stepと同じ(state,reward,done,info)を受け取り、info.planningに候補内訳を持たせる案。通信名/API名は実装時に確定する。既存step(x)は維持する。action_idの予約・再送キャッシュを共用/拡張し、同じ命令の再送で再探索・再落下しない。設定の違う命令を同じIDで再送した場合はconflictにする。timeoutで実行結果不明ならresetで復旧する。

## 9. 計算量、比較試験、残る制約

初版は1候補ずつ既存方式で生成/解放する。計算時間は候補数×1候補時間を見積もりに使えるが、実際には全体の平均/p95、描画停止時間、解放待ちの増大を計測する。単一候補の計算途中は中断しない。ソフト予算を使う場合は候補間で判定し、未評価を明示する。候補数を増やすだけで無条件に高速・高精度になるとは扱わない。

実装後の短時間テストには、空盤面のH/D/R=0、保持/NEXT除外、未接触と跳ねた果物、実Colliderの回転/Offset、H/D/Rの正規化範囲、接触面の区間境界、GO除外/全GO/失敗混在、各加点区間の保存則、再送による1回だけの落下、安全範囲、設定変更を含める。

同一開始盤面でpost_drop_stepsを25/50/100、候補数を5/9/11/21/31に変え、各特徴・選択X・得点・GO・計算時間がどう変わるか比較できるようにする。複数候補の予測だけなら同じ受付内でライブ盤面を進めず比較できる。複数の実ゲーム結果を公平に比較するには同一開始条件のfixture/再現条件が別途必要であり、連続した異なる盤面を同一条件と呼ばない。短時間の回帰確認後、長期の得点分布・GO率・手数・時間と移動中自然加点の影響はユーザーが検証する。

PhysicsScene2Dの接触履歴、物理更新と描画/Destroy境界、短い予測窓の限界は残る。GO=falseは安全保証ではなく、Dの危険帯も見逃しを解消する保証はない。精度を装うためのGO条件変更・物理更新数の補正は行わない。

開発順序はSTEP 5=1手先探索、STEP 6=複数ゲーム並列、STEP 7=Value Network、STEP 8=MCTSを維持する。長期の複数AIモード・高速無描画・モデル保存再開は開発計画の目標のまま。STEP 5まで実装し、STEP 6以降には進まない。今回commit・pushはしない。

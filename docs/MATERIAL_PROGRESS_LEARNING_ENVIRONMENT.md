# 材料育成の進捗を学ぶ環境（2026-11-11）

## 設計

現時点で有望と考える実験環境であり、最適性・ダブルスイカ達成率の改善は未確認。
通常ゲームの経験を維持しつつ、スイカが存在する盤面で次の大きな果物を育てる経験を増やす。
特定位置への攻略報酬や、盤面が必ず救済できるという仮定は導入しない。

観測する条件は次の7種類。必ず順番に通る階段ではなく、独立した共存条件・成果として扱う。

1. スイカ1個
2. スイカ＋パイナップル
3. スイカ＋メロン
4. スイカ＋メロン＋パイナップル
5. スイカ＋メロン2個
6. スイカ2個
7. スイカ同士の合体・消滅（ダブルスイカ）

果物の種類は既存Prefabで確認：パイナップル8、メロン9、スイカ10。
材料が育ったこと自体を中間成果として記録し、到達後の生存落下数・追加得点も併せて評価する。
盤面形状次第で合体まで到達できないこともあるため、材料数を成功確率としては扱わない。

## 原子的な実ゲーム観測

`SuikaMaterialProgress` は実ゲームの既存Drop/Merge通知を利用するカウンターのみの処理。
予測Sceneから呼ばれず、オブジェクト・乱数・物理・得点を変更しない。
`material_progress=true` の実験用Labでのみ開始する。標準プレイでは未開始。

近似盤面を読み込んだ直後に、保持果物を除く配置済み全果物の数を初期値として設定する。
最初から成立していた条件は `initial=true`。新規達成・追加学習報酬として数えない。
同じ条件は1ゲームに一度だけ記録。合体後の個数更新と条件判定を一つの通知内で実行し、
同一物理時刻にメロン2個→スイカ2個→消滅しても途中の成果を保持する。
各初回イベントにtick、fixed_time、得点、落下数、パイナップル/メロン/スイカ数を保存する。

既存の古い `learning` カウンターは近似盤面の初期果物を把握できない場合があるため、
新観測では初期値を明示的に設定して区別する。旧カウンターの既知フラグだけで近似盤面の未達を断定しない。
カウンター不整合時はunknownとして扱う。初期公開盤面と取り込み後の比較監査も維持する。

新Player：`Unity/Builds/MaterialCurriculum_01/SuikaGameAI.exe`
旧 `PolicySelfPlay_01` 等は変更していない。
新Playerでも観測OFF時は、JsonUtilityが既定フィールドを出力する場合がある。利用可否はフィールドの存在ではなく `known` で判定する。

## 練習セット

`Python/outputs/watermelon_material_curriculum_20261111_01/`

承認済みTrainのスイカ成功元ゲームをseed順に最大64群調べ、材料条件の被覆を優先して24群を固定した。
同じ元seedまたは初期8果物系列の重複を独立盤面として数えない。
各条件が最初に観測された判断開始時点とスイカ生成前を採取。
同じ公開状態が複数条件を満たす場合は同一snapshotとして管理する。最終得点や続行成績による選別はしていない。

| 条件 | 利用できる独立元ゲーム群 |
|---|---:|
| 生成直前 | 24 |
| スイカあり | 24 |
| スイカ＋パイナップル | 16 |
| スイカ＋メロン | 4 |
| スイカ＋メロン＋パイナップル | 0 |
| スイカ＋メロン2個 | 0 |
| スイカ2個 | 0 |

条件は重複する。ユニークな近似盤面は64枚。
0は今回調べた元ゲームの**保存済み判断時点では確認できなかった**という意味で、瞬間的な共存まで否定しない。
存在しない果物や成功盤面を合成して埋めない。

通常開始と近似開始をジョブ単位で交互に投入する。
近似開始は利用できる条件を巡回し、条件内で元ゲームを巡回して未来seed・探索seedを変える。
現セットでは生成前／スイカあり／＋パイナップル／＋メロンの4条件。
終盤の最後の1盤面だけを大量に反復する設計を避けた。稀な条件では同じ元ゲームの反復が増えるが独立群数は増やさない。
50:50は投入ゲーム数の暫定比率で、計算時間や判断数の比率ではない。

既存137,849状態のreplayはSHA付きの読み取り専用参照として再利用し、1.1 GiBの複製を作らない。
厳密な過去ゲームの再開ではなくcold reconstruction。接触キャッシュ・元の隠れた物理状態・元の未来乱数は復元していない。

## 実行コマンド

本開発では長時間収集を開始していない。以下はユーザーが開始する20時間・4並列の例。
データセットmanifestから新Playerとprogress-balanced方式が選ばれる。

```powershell
Set-Location C:\SuikaGameAI\Python
$tag = (Get-Date -Format "yyyyMMdd_HHmmss") + "_" + [guid]::NewGuid().ToString("N").Substring(0,8)
$out = "outputs\watermelon_material_practice_$tag"
Write-Host "保存先: $out"

.\.venv\Scripts\python.exe .\double_watermelon_learning.py collect `
    --dataset .\outputs\watermelon_material_curriculum_20261111_01 `
    --output $out `
    --model .\outputs\rollout_selfplay_20261106_021012_897a0c88\generations\gen_e06d5505dd2c\model.json `
    --workers 4 `
    --hours 20 `
    --progress-bonus-points 10
```

MCTS256反復・深さ4・固定5候補・既存学習rollout50%を維持し、ゲーム中にモデルを更新しない。
1ゲームの安全上限は4時間/100,000落下、ログ無進捗watchdog720秒。720秒はUDP応答timeoutではない。
20時間は新規投入停止時刻。実行中ゲームをdrainし、その後学習するので全終了は遅れる。
空き4 GiB未満では開始拒否、収集中2 GiB未満で新規投入停止。
既存Playerがあれば起動拒否し、既存収集を止めない。ポート44800〜44807。

Ctrl+C 1回：新規投入を止めて進行中ゲームを待つ。2回：自分のPlayerを止めて部分ログを保存する。
2回目で強制停止した場合は、自動学習もスキップする。完了済みデータは後で手動学習に使える。
再開は同じoutputで `--resume` を追加する。完了済みゲームは再実行せず、途中ゲームは新attemptで最初から再実行。
途中ネイティブ状態の厳密再開ではない。20時間の残り予算を使い、追加20時間には新しいoutputを使う。

```powershell
.\.venv\Scripts\python.exe .\double_watermelon_learning.py summary --output $out
```

通常開始と近似開始を分けて、自然GO追加得点・各条件の初期成立数・新規到達数・評価可能分母・unknown数・
到達後の平均生存落下数・追加得点を表示する。
実験結果の `material_progress.goals.*.first` と生traceから、達成以前の判断を追跡できる。
途中打ち切りは自然GO returnの教師にしない。古い部分観測の「不明」を失敗に置き換えない。
旧ログでは陽性だけ観測できた条件もあり、unknownを除いたobserved_rateは母集団の達成率と同一視しない。

## 学習

現在は小型方策の結果重み付き模倣学習であり、最適行動の直接教師や価値ネットワークではない。
既存の訪問分布75%＋実行行動25%、cross-fit状態baseline、群単位重み、最大64状態/episodeを維持する。
新しい予測入力は増やさず、未来情報は教師側だけに置く。

`--progress-bonus-points 10` の場合、収集後に同じ経験から次の2モデルを別保存する。

- 通常の実ゲーム追加得点によるモデル（ボーナスOFF）
- 原子的観測が自然GOまで完全なゲームに限り、中間成果ボーナスも使う実験モデル

| 初回の新規成果 | 学習用追加点（unit=10の試案） |
|---|---:|
| 最初のスイカ | 0（既存の合体得点は通常通り） |
| ＋パイナップル | 10 |
| ＋メロン | 20 |
| ＋メロン＋パイナップル | 30 |
| ＋メロン2個 | 40 |
| スイカ2個 | 60 |
| ダブルスイカ | 200 |

これは最適化済みの数値ではない。`--progress-bonus-points 0` でOFF、他の数値で一括変更できる。
各成果は一度だけ加算し、初期盤面の成果や判断時点で達成済みの成果には追加しない。
複数条件を達成した場合は合計する。単一成果ではダブルスイカが最大。
**実ゲーム得点・MCTSの報酬・物理は変えない。** 学習用returnだけを別計算し、行動重みは0.5〜2に制限する。
`learning_labels.jsonl` に実ゲームreturn、学習用bonus、学習用return、known mask、元groupを分離して保存する。
完全性の不明な古いログは通常得点の学習に残すが、中間ボーナスの重み付けには使用しない。

Validationのモデル選択指標は両方式とも通常得点由来の重みを使う模倣損失に統一する。
この指標は実ゲーム得点そのものではない。ボーナスで通常得点が下がる可能性があり、実ゲーム検証が必要。
両モデルとも自動昇格せず、保存された旧actorは変更しない。次のセッションで明示指定して使う。
同じmanifestの過去の完了練習セッションも開始時点で固定し、累積replayに使用する。
反復数を独立盤面数として水増しせず、同じ元ゲーム・系列の群はTrain/Validationをまたがせない。

既存のTest予約manifestは削除されており、旧Test系列の完全な復旧はしていない。
承認済みTrain/Validationと既知の除外seedを利用するが、失われた予約系列の完全隔離や新しい独立Testの評価を主張しない。

## 確認結果と限界

- 新しい材料観測20項目、従来ルール127項目、MCTS861項目が成功。
- 旧Player／新Player観測OFF／新Player観測ONの各3手で、全記録時相の比較公開状態、操作tick、実ゲームRNG、root統計が一致。
  生成されたオブジェクトIDは物理比較から除外。3手の一致から長時間完全一致は主張しない。
- 4並列・8試行を各1落下で終了。通常開始と4種類の近似開始、初期果物数、材料観測、256反復、予測Scene残留0を確認。
  生成前の1試行で新規スイカを観測。最初から存在する＋パイナップル／＋メロンは新規成果に数えないことを確認。
- 別の短い終盤確認で1落下自然GO。新規成果0、完全な負例として記録し、ボーナスOFF/ONの両モデルを自動学習・別保存できた。
  各約36〜38秒、各39,880状態。非ゼロの中間ボーナス対象は0件で、実経験からのボーナス学習効果はまだ検証できない。
- 非ゼロbonusの計算・初期成果除外・未来教師分離・打ち切り除外は専用unit testで検証。
- 保存した実験モデルを新Playerで読み込み、2並列・各1落下のMCTS内推論も成功。
- Python新環境36項目が成功。全体テストには削除済みTest予約manifestに依存する既存1件のエラーが残る。
- 長時間収集、通常開始からの得点改善、2個目生成率・ダブル達成率の改善は未検証。大規模実験は実行していない。
